## 1. Acquisition tools × platforms

There are two tools (Cellebrite, GrayKey) and two platforms (iOS, Android),
giving four combinations. In the code, though, a case is described by an
**archive layout** (`FfsAdapter.format`), not by a tool, and Cellebrite
Android has been seen in **two** different layouts. So the code really deals
with five cases:

| # | Combination | `FfsAdapter.format` | Seen on real archive |
|---|---|---|---|
| A | Cellebrite iOS | `cellebrite` | IOS17 JoshHickman; iOS 16.5 CTF23 Cellebrite |
| B | GrayKey iOS | `graykey` | IOS18 CTF25 Magnet |
| C | GrayKey Android | `graykey` | Android 14 CTF26 Magnet |
| D1 | Cellebrite Android, `Dump/` layout | `zip_extras` | Android 14 JoshHickman (as recorded in `CLAUDE.md` history; not re-checked for this document) |
| D2 | Cellebrite Android, `filesystemN/` layout | `cellebrite` | Android 15 CTF25 Cellebrite |

**A-1. Format is a layout, not a tool.** *Confirmed (real).*
The "CTF26 Magnet" archives (B and C) are labelled Magnet but detect as
`graykey`, and the Cellebrite Android archive in D2 detects as `cellebrite`,
the same as iOS. Never present `.format` to an examiner as "acquired with
tool X". `artifacts/*/device_info.py` labels it as an "archive layout" for
this reason.

**A-2. The format alone does not tell you the platform.** *Confirmed (real).*
`graykey` covers B and C; `cellebrite` covers A and D2. Only `zip_extras` is
unambiguously Android.
- Platform is decided by `FfsAdapter.is_android(folder_map)`: true for
  `zip_extras`; otherwise true only if `data/data` is in the folder map.
- `data/data` was confirmed absent from every real iOS archive checked.
- With no folder map yet (some first-parse callers), it falls back to "iOS".
  A caller that never passes the folder map will treat C and D2 as iOS.
- Relied on by: `container_parents()`, `bundle_id_for_path()`, app
  intelligence / App Report, MCP `list_apps`, the User Media filter, scan
  rules. `container_bundle_id()` uses a local version of the same test (does
  the path start with `data/data/`).

## 2. How each layout is detected

Detection is `FfsAdapter.detect()` (`app/adapters/ffs.py`), tried in this order.

| Order | Test | Result |
|---|---|---|
| 1 | Any of the **first 20** entries carries a GrayKey extra-field block (tag `GK`, or the older tag `0x0004`) | `graykey`, user prefix `private/var` |
| 2 | Some entry starts with `Dump/` **and** one of the first 20 entries has a UT (Unix timestamp) extra block | `zip_extras`, user prefix `Dump` |
| 3 | Anything else | `cellebrite` (see below) |

For `cellebrite`, the user and system partitions are found by name:
- **User partition:** the first `filesystemN/` (N = 1–9) containing `mobile/`
  or `wireless/` directly (new layout). Failing that, the first containing
  `private/var/mobile/` or `private/var/wireless/` (old layout,
  `old_layout = True`). Failing both, `filesystem2`, new layout.
  - The new layout is checked across all N first, because the iOS system
    partition can hold a few stub entries under `private/var/mobile/` that
    would otherwise be mistaken for an old-layout user partition.
- **System partition:** the first `filesystemN/` containing `System/Library`
  or `System/`. Failing that, `filesystem1`.

**A-3. Detection heuristics.** *Code only, except where noted.*
- **GrayKey is decided from the first 20 entries.** A GrayKey zip whose first
  20 entries carry no `GK` block would be misread as Cellebrite. *Unverified.*
- **Only GrayKey block version 1 is understood.** Any other version raises
  `ValueError` while parsing metadata, which stops the whole metadata build
  rather than skipping one entry.
- **Cellebrite is the default.** An archive from any other tool (or a plain
  zip) is treated as Cellebrite and falls back to `filesystem2`. Nothing tells
  the examiner the layout wasn't actually recognised.
- **D2's user partition is unconfirmed.** An Android `filesystemN/` archive
  has no `mobile/` or `wireless/` folder, so the user-partition search
  presumably falls through to the `filesystem2` default. This is
  *unverified*: see open question Q2.

## 3. Paths: what is stored, what is shown, how they map

Three kinds of path appear in the code:
- **physical**: the zip entry name;
- **ui_path**: the path the code works with and the tree is built from;
- **display**: what the examiner sees, e.g. with a GUID replaced by an app
  name.

Never mix physical and ui_path. Convert with `FfsAdapter.resolve()` (ui_path →
physical) and `strip_display_prefix()` (physical → display-style).

| | Physical entry (example) | ui_path | `resolve(ui_path)` |
|---|---|---|---|
| A Cellebrite iOS, new layout | `filesystem2/mobile/Library/SMS/sms.db` | `mobile/Library/SMS/sms.db` | `filesystem2/` + ui_path |
| A Cellebrite iOS, old layout | `filesystem2/private/var/mobile/Library/SMS/sms.db` | `mobile/Library/SMS/sms.db` | `filesystem2/private/var/` + ui_path |
| B GrayKey iOS | `/private/var/mobile/Library/SMS/sms.db` | `private/var/mobile/Library/SMS/sms.db` | `/` + ui_path |
| C GrayKey Android | `/data/data/com.whatsapp/…` | `data/data/com.whatsapp/…` | `/` + ui_path |
| D1 Cellebrite Android (`Dump/`) | `Dump/data/data/com.whatsapp/…` | `data/data/com.whatsapp/…` | `Dump/` + ui_path |
| D2 Cellebrite Android (`filesystemN/`) | `filesystemN/…` | everything after `filesystemN/` | as A (unverified, Q2) |

**A-4. Cellebrite iOS ui_paths start at the user partition root;
GrayKey iOS ui_paths keep `private/var/`.** *Code only.*
- The same file is `mobile/…` on Cellebrite but `private/var/mobile/…` on
  GrayKey.
- Any fixed iOS path written in code or config is stored in Cellebrite form
  and adapted per case by `prefix_shortcut()`. Examples are scan rules,
  forensic shortcuts and parser `app_path`s; `prefix_shortcut()` adds
  `private/var/` for GrayKey.
- Container parents differ the same way: `mobile/Containers/…` versus
  `private/var/mobile/Containers/…`.
- `strip_display_prefix()` removes the GrayKey `private/var/` again for
  display.
- **Discrepancy to fix in `CLAUDE.md`:** its section 1 says GrayKey "always
  needs a `private/var/` prefix prepended to a ui_path before it resolves".
  In the code, the ui_path *already contains* `private/var/`; what gets
  prefixed is the Cellebrite-form shortcut path.

**A-5. GrayKey zip entry names start with `/`.** *Code only.*
`resolve()` prepends `/`, and GrayKey metadata keys are stored with the
leading `/` stripped.

**A-6. Old-layout Cellebrite is folded into new-layout paths.** *Code only.*
Old-layout archives keep `private/var/` in both the zip paths and the
`metadata.msgpack` keys. Both are stripped, so the ui_paths look identical to
a new-layout archive. As a result, `private/var/mobile` and `private/var/root`
appear as just `mobile` and `root`. This matters when importing paths from
other tools such as Griffeye; see `ios_path_candidates` in
`app/spreadsheet_import.py`.

**A-7. Cellebrite shortens some path segments in the zip itself
("truncation").** *Code only; the cause is not recorded anywhere (Q1).*
- In Cellebrite iOS archives, some path segments look different in
  `metadata.msgpack` (the manifest) and in the zip.
  - Manifest: `<readable part>-<32 or more hex characters>`.
  - Zip: only the trailing hex characters.
- `resolve()` reproduces this. Any ui_path segment containing `-` whose part
  after the last `-` is at least 32 hex characters is cut down to that hex
  part.
- Consequences:
  - The tree and the file browser are built from the **zip's** names (see
    A-9), so the examiner sees the shortened hex form, not the readable name
    in the manifest.
  - To attach manifest metadata to these entries, `build_ui_metadata()` builds
    a second index keyed by `resolve(manifest key)` (`guid_meta`).
  - A path that already holds only the hex form passes through `resolve()`
    unchanged.
  - A normal iOS container GUID (`8-4-4-4-12` hex) is never shortened: its
    last group is only 12 characters.
- Risk: any genuine filename on the device matching the pattern
  `…-<32+ hex>` would also be shortened by `resolve()`, and then not found in
  the zip. *Unverified whether such names occur.*
- Applies only to `cellebrite`. GrayKey and `zip_extras` paths are used as-is.

**A-8. iOS app containers are GUID-named; Android ones are package-named.**
*Confirmed (real).*
- On iOS (A, B), `Containers/Data/Application/<GUID>` etc. are mapped to
  bundle ids. The main source is the LaunchServices csstore, topped up from
  each container's
  `.com.apple.mobile_container_manager.metadata.plist`.
  - The csstore was confirmed sometimes needed because the per-container
    plists are missing on GrayKey extractions.
  - A GUID is specific to one installation. Anything stored across cases must
    use the bundle id: `FfsAdapter.canonical_app_path()`.
- Android (C, D1, D2) uses `data/data/<package>` directly, with no mapping.

## 4. What each layout provides

| | A Cellebrite iOS | B GrayKey iOS | C GrayKey Android | D1 Cellebrite Android (`Dump/`) | D2 Cellebrite Android (`filesystemN/`) |
|---|---|---|---|---|---|
| File metadata source | `metadata2/` or `metadata1/metadata.msgpack` | zip extra fields (GK/UT/UX/inode) | zip extra fields (GK/UT/UX/inode) | UT extra field only | presumably msgpack, as A (Q2) |
| Timestamps | as recorded in the msgpack (stored as ns) | mtime/atime/ctime/btime; whole seconds (32-bit UT values) | as B | **mtime only**; atime/ctime/btime are always 0 | as A (Q2) |
| uid/gid, inode, xattrs | from msgpack | from UX/inode/GK blocks | as B | none: the UX block is present but uid/gid are 0 on every entry; the Unix mode in the external attributes only marks file vs folder (all permission bits 0); no symlinks | as A (Q2) |
| Per-file hashes | none | SHA-256, optionally SHA-1 + MD5 (A-73) | as B | none (CRC-32 only) | (Q2) |
| What the tree contains | **user partition only** | every entry in the zip | every entry in the zip | everything under `Dump/` | the detected `filesystemN/` only (Q2) |
| System partition files | not in the tree; read only for device info via `system_candidates()` | in the tree (no separate partition) | in the tree | under `Dump/` | (Q2) |
| GUID → bundle-id map | yes | yes | no | no | no |
| Capture record (integrity check) | `<zip name>.ufd` | `<zip>.sha256`, else a GrayKey PDF report named after the device UDID | as B | `.ufd` | `.ufd` |
| Acquisition-machine timezone guess | from the `.ufd` UTC offset | none | none | from the `.ufd` | from the `.ufd` |
| Handset timezone | from `private/var/db/timezone/localtime` | same | none found on Android | none | none |
| Excluded from keyword search | `metadata1/`, `metadata2/` | — | — | — | `metadata1/`, `metadata2/` |

**A-9. In Cellebrite iOS, the zip decides what exists.** *Code only.*
The tree is built from the zip's own entries. The msgpack only adds metadata
to entries the zip already has: anything listed in the msgpack but not in the
zip never appears. In GrayKey and `zip_extras`, the metadata is read from the
zip entries themselves, so the two can't disagree.

**A-10. A missing UT block in GrayKey falls back to the zip's DOS time,
treated as UTC.** *Code only.*
Applies to B and C. The zip's DOS timestamp has no timezone and only 2-second
precision, so if a tool wrote local time there, those mtimes would be shifted
by the acquisition machine's offset. A UT block that is present with mtime 0
is kept as 0 (shown as `---`), not replaced.

**A-11. 32-bit UT timestamps.** *Code only.*
GrayKey and `zip_extras` times are unsigned 32-bit seconds: no sub-second
precision, and nothing representable before 1970 or after 2106.

**A-67. Which layouts' inode numbers can be trusted.** *Confirmed (real),
2026-10-16.*
- **B, C (GrayKey):** inode + device ID from the zip extra field's `0x4e49`
  block. The device ID is required: inode numbers alone collided across
  Android's separate filesystems (CTF26: `mmssms.db-wal` shared a number
  with an unrelated `.apk`). With both, no false matches were found.
- **A, new layout:** only the user partition's msgpack is loaded, and its
  inode numbers didn't collide (iOS16.5 CTF23 Cellebrite: 5,046 same-file
  groups, zero size mismatches). There is no device ID, so the bare inode
  is shown.
- **A, old layout:** not reliable. One merged msgpack covers both
  partitions; in IOS17 JoshHickman 2,499 of 10,869 same-inode groups (23%)
  were unrelated files. Never used.
- **D1:** no inode data (zero `0x4e49` blocks in ~288K entries).
- Relied on by: `FfsAdapter.inode_trusted`, which gates both the File
  Browser "Inode" column and the duplicate scan's inode shortcut (A-69).
  The inode is shown for manual filtering only; nothing else infers
  identity from it.

**A-68. "Accessed" and "Link Count" columns appear only when the data is
real.** *Confirmed (real), 2026-10-16.*
- Both are decided by sampling up to 500 entries at load, not by format.
- **Accessed (atime):** real on B, C and both A layouts. On D1 the UT
  block's atime flag is set but the value is always 0, so it's hidden.
- **Link Count (hardlinks):** stored only in A's msgpack (both layouts);
  GrayKey never records it. Named "Link Count" to avoid confusion with
  "Linked Report".

**A-72. A zip can store the same path twice; the app shows one copy.**
*Confirmed (real), 2026-10-20.*
- GrayKey zips do this: CTF26 has 37 repeated paths (20 files, 17 folders),
  IOS18 has 85 repeated file paths. Cellebrite archives had none.
- Most copies are identical (same size and CRC). One is not: IOS18's
  `private/var/mobile/Library/Mail/Envelope Index-wal` was captured twice,
  54 s apart (1,256,632 vs 1,268,992 bytes), because the WAL changed during
  acquisition.
- Why: GrayKey appears to collect key databases in an early pass, then
  again in its full file-system walk. On IOS18, 18 database families have
  the database and WAL in both passes and the SHM only in the second;
  the keychain's WAL and SHM were written once, next to its first copy.
- *Decision (owner), 2026-10-20:* show every copy. `zip_cd_cache` gives each
  earlier copy its own name, e.g. `sms [capture 1 of 2].db`,
  `Envelope Index [capture 1 of 2]-wal`; the last copy keeps the real name
  (what the app always showed). A "Capture" column ("1 of 2"/"2 of 2")
  appears on archives that have repeats.
- *Decision (owner):* a database copy uses the WAL/SHM from its own capture,
  never another's. The shared base name does this in the SQLite viewer; a
  sidecar written once keeps its real name, so the main database still uses
  it. A copy with no WAL of its own says so, and names the capture that has
  one.
- Parsers use only the real-named (latest) set by default; earlier captures
  are skipped by `is_capture_alias`. *Decision (owner), 2026-10-21:* no
  automatic re-run on earlier captures. Instead the parser run log (only
  there) warns for each file a parser read — or that file's -wal/-shm/
  -journal — that has an earlier capture, naming the copy to review.
  Verified: SMS parser on IOS18 warns for sms.db and sms.db-wal; on IOS17
  (Cellebrite) no warning.
- Verified on IOS18 and CTF26: every renamed copy reads at the right offset
  with a matching CRC; no file path is repeated after renaming; the four
  Cellebrite archives are unchanged.

**A-73. Per-file hashes: GrayKey records them, Cellebrite doesn't.**
*Confirmed (real), 2026-10-20.*
- GrayKey stores tagged extra-field blocks per file: `S2` = SHA-256 (32
  bytes), `S1` = SHA-1 (20), `MD` = MD5 (16). Which ones appear depends on
  the archive (CTF26: S2 only; IOS18: all three). Folders have none.
- Three copies per file: the local header holds an all-zero placeholder
  (GrayKey streams the file before it knows the hash); the trailer after
  the data repeats the real values (A-15); the central directory holds the
  real values. `graykey.py` parses the central-directory copy.
- Evidence: every file entry in both archives has `S2`; the CD values equal
  the trailer bytes for every entry; recomputed hashes matched on 4,116
  sampled files, and 1,598 more through the parsed metadata.
- Used for: the "SHA-256/SHA-1/MD5 (GrayKey)" File Browser columns and the
  duplicate scan (A-69). Not used to verify files (owner's choice,
  2026-10-20).
- Cellebrite: no per-file hash anywhere (msgpack, extra fields, trailers,
  `.ufd`, side files). Only the zip's CRC-32 per file and the whole zip's
  SHA-256 in the `.ufd`. Cellebrite Android zips also hold
  `extra/Secrets/secrets.json` (per-app script output, not file metadata)
  and, on Android 15 CTF25, `extra/Secrets/gen_mem.dat` (unidentified).

## 5. The main FFS zip itself

These are what allow the app's own direct-seek zip reader (`ZipEntry`,
`ZipReader`, `zip_cd_cache.compute_data_offsets`) to skip the checks Python's
`zipfile` makes. That is where the speed comes from. See the review dated
2026-10-20.

**A-12. Entries are never compressed.** *Examiner; Confirmed (real) on all
six test archives, 2026-10-20: 0 of 2,158,435 entries compressed (CTF26,
IOS18, CTF23, IOS17, Android 14 JoshHickman, Android 15 CTF25).*
- Relied on by: every direct-offset reader, i.e. the header scan, EXIF/video
  metadata scan, keyword search, hex view and export.
- If wrong: those readers would return compressed bytes as if they were the
  file. Keyword search filters out non-stored entries, so such files would be
  silently not searched, which the Search Coverage dialog does not mention.
  `ZipEntry` alone would still work, but very slowly.
- No runtime check exists.

**A-13. The zip never changes after acquisition.** *Examiner.*
- Relied on by: the `.zcd` central-directory sidecar, which is built once
  and never re-checked against the zip on normal opens.
  `_verify_archive_matches_case` runs only when an archive is relocated.
- If wrong: every read would land at the wrong position.

**A-14. Entries are not encrypted.** *Examiner.*
If wrong, encrypted bytes would be returned as the file. No check exists.

**A-15. Files are stored back to back in the zip, each followed by a
fixed-size trailer.** *Confirmed (real), 2026-10-20, on all six test
archives (every entry checked against its own local header).*
- After each file's data comes exactly the tool's trailer, then the next
  entry's header. Nothing else, no gaps:
  | Tool | Trailer after the data | Bytes |
  |---|---|---|
  | Cellebrite (iOS and Android) | ZIP64 data descriptor, on every entry | 24 |
  | GrayKey, SHA-256 only (CTF26) | 16-byte data descriptor + the file's SHA-256 (A-73); none after folders | 48 |
  | GrayKey, three hashes (IOS18) | descriptor + SHA-256 + SHA-1 + MD5 | 84 |
- The local header's extra field differs from the central directory's by a
  fixed amount per CD ZIP64-block length (GrayKey: 0 before 4 GiB, -12
  past it; Cellebrite: +20 and +8, because its local headers carry their
  own ZIP64 sizes block). One Android 15 CTF25 file over 4 GiB has its own
  group (+24-byte CD block, -8).
- `compute_data_offsets` learns both per archive from a sample of real
  headers (about 100 reads), then derives every entry's data offset with
  no I/O. An entry is accepted only if the trailer it implies equals the
  learned one for its class; anything else is read from its own header.
  Result on all six: 0 wrong offsets in 2,158,435 entries; 95-127 header
  reads per archive; CRC-32 matched on ~13,300 sampled files (10 GB).
- Residual risk: a derived offset can only be wrong if one entry has both
  an unseen header shape and an unseen trailer size that cancel exactly.
  None of the entries checked had either.
- If wrong: offsets would shift, as in A-16. Guarded by the per-entry
  trailer check above.

**A-16. ZIP64 appears in every large FFS zip.** *Reasoned from the zip
format; reproduced on a synthetic archive.*
Archives over 4 GiB must store the real header position of every entry past
the 4 GiB mark in a ZIP64 block in the central directory, which the local
header doesn't have. This is what made the old single-delta offset
calculation 12 bytes wrong for one group of entries. Fixed in
`zip_cd_cache.py` (KlasScripts/FFS-Explorer#2 and the follow-up commit).
*Confirmed (real), 2026-10-20:* all six test archives are over 4 GiB; the old
code (5 runs each) placed files wrong on five of them, depending on its
random sample: up to 164,079 on CTF23, 37,975 on IOS18, 31,457 on Android 14
JoshHickman, 27,263 on Android 15 CTF25, 4,406 on CTF26 (IOS17 escaped by
luck). Header-scan types stored before v0.45.0 may be wrong for those files.

**A-17. CRC is not verified on reads.** *Decision, not a fact.*
Deliberate, for speed. It is acceptable only because acquisition integrity is
established separately: the integrity check compares the whole zip's SHA256
with the capture record (section 4 table). If that check isn't run, nothing detects
a corrupted entry.

**A-18. The main zip is never read with raw `zipfile`.** *Decision.*
- Reads go through the sidecar plus `ZipEntry`, because a `zipfile` open
  re-parses the whole central directory, which takes seconds on a large or
  network-hosted archive.
- Allowed exceptions: `ZipEntry`'s own compressed-entry fallback, and
  already-extracted local files (nested archives).

## 6. Nested archives (embedded zip/gzip files)

**A-19. Repacked nested archives are uncompressed and written once.** *Code
only.*
- `nested_archive.extract_one` rewrites an embedded zip entry by entry as a
  new `ZIP_STORED` zip in `case_dir/nested_archives/<12-char hash>_<name>`,
  skipping directory entries.
- An embedded gzip is stored as its raw decompressed bytes, which is not a
  zip.
- Nothing modifies these files afterwards, except a re-extraction.
- Relied on by: `read_nested_entry`'s cached per-archive index, read by
  direct seek; the index is rebuilt if the file's mtime or size changes.
- If wrong: a stale index would read the wrong bytes. Mitigated by the
  mtime/size check.

**A-20. Embedded archives are never extracted automatically.** *Decision.*
Extraction is an examiner action (Process Case, or right-click), or is
declared by a parser through `requires_nested_extraction`. Content inside an
unextracted embedded archive is invisible to search and parsers; `list_apps`
reports it as `embedded_archives` so the gap is visible.

## 7. Other data facts the design relies on

**A-21. Evidence timestamps are UTC.** *Decision, plus Code only for each
source.*
- All evidence times are shown as labelled UTC by default; other zones are
  opt-in per case.
- Each source is assumed to be UTC as stored: msgpack times, UT fields, the
  DOS fallback (A-10), and app database epochs.
- Parsers store raw values and declare the unit (`timestamp_fields`).
- The other zones a case can opt into: the **handset's** zone (read from the
  device, iOS only); the **acquisition machine's** zone (guessed from the
  `.ufd` offset, A-23); or one chosen **manually** (starts blank, never
  auto-picked).
- The active mode is shown in exactly one place: a banner above every tab.
  Never repeat it per column.
- A tool-provenance time ("when did the examiner do X") is different: shown
  in local time with an explicit UTC-offset label.

**A-22. The handset timezone is only a snapshot.** *Confirmed (real).*
The iOS `localtime` file gives the zone at acquisition. Ground-truth images
show devices changing zone over time, so it doesn't apply to older evidence
automatically.

**A-23. The acquisition machine's timezone is never recorded.** *Confirmed
(real) on two cases.*
Only a UTC offset exists, in the `.ufd`, so the zone is guessed from that
offset and must be confirmed by the examiner. GrayKey provides no offset.

**A-24. Header-scan scope comes from one shared ruleset.** *Decision.*
`config/scan_rules_ios.json` and `scan_rules_android.json` (via
`scan_rules.py`) decide which folders the header scan, nested-archive
discovery and the embedded-media sweep cover. For GrayKey, both platforms'
iOS and Android rules are applied, because the format can't say which
platform the archive is (A-2).

## 8. Header-scan tiers and scan scope

**A-25. File type comes from the extension unless the header scan corrects
it, and everything reads the same correction.** *Decision.*
- Extension-based typing is sometimes wrong (a renamed database; a `.bin` MMS
  part that is really a JPEG). The header scan reads real magic bytes.
- One dict, `_header_type_overrides`, holds the result. Everything that needs
  "what is this file really" reads it: the Type column, the Search Coverage
  reminder, the embedded-media sweep's candidate list, the raw preview.
  Decoded LevelDB records write their type into the same dict.
- Never add a second, independent type guess.

**A-26. Tiers.** *Decision.*

| Tier | Scope |
|---|---|
| 0 | Off: extension-based typing only |
| 1 | Unknown-extension files, app/user-accessible areas |
| 2 | All files, app/user-accessible areas |
| 3 | All files, everywhere |

- Stored per case: `header_scan_tier` and `header_scan_complete_tier` in
  `case_settings`.
- A new case starts at tier 0. Nothing runs automatically; Process Case
  offers Tier 1, pre-ticked.
- `_HEADER_SCAN_TIER_TEXT` (and its shared coverage dict) is the one
  description of what each tier covers. The Search Coverage dialog and
  Process Case read it; never keep a second copy.
- The Search Coverage reminder states the current tier, what it does and
  doesn't check, and what a low tier risks missing (a renamed archive or
  database).

**A-27. One shared folder ruleset.** *Decision, 2026-10-10.*
- `app/scan_rules.py` reads `config/scan_rules_ios.json` and
  `scan_rules_android.json`. Behind it are `FfsAdapter.scan_folders()`,
  `scan_excludes()`, `user_media_folders()` and `embedded_media_excludes()`.
- Why: four hand-maintained lists had already drifted apart by accident
  (archive discovery was missing folders the header scan had).
- One row per folder prefix:
  `{"path", "include": 1|0, "user_media": "not_user_media"|"user_media_only"|"also_user_media", "embedded_media_exclude": 1}`
  (the last key is optional).
  - `include` is the shared scope for header-scan tiers 1–2, nested-archive
    discovery and the embedded sqlite/plist sweep. All three want the same
    "user data or system noise" answer.
  - `user_media` is independent and deliberately narrower: used only by the
    Media Browser's "User Media" filter, a precision view.
  - `embedded_media_exclude` removes a folder from the embedded sweep only
    (that sweep parses every sqlite/plist, so it can be too costly where the
    header scan is still cheap).
- Paths are stored in Cellebrite form; `prefix_shortcut()` adapts them for
  GrayKey. Rules are split by platform, since a case is one platform and the
  two share no folder vocabulary. For GrayKey both sets apply (A-2, A-24).
- There is deliberately no "User Media exclude" rule field: that already
  exists as `user_media_ignore_list.py` (A-34). One was added and removed the
  same day for duplicating it.

**A-28. What counts as an excludable "noise" folder.** *Confirmed (real),
2026-10-10, refined twice by the project owner.*
- Both must hold:
  1. No recognisable content at all: every unknown-extension file
     magic-checked and classified as nothing. "No media" is not enough;
     the first attempt checked only for pictures/video/audio and wrongly
     excluded 19 folders that held real JSON, plist, database, archive or
     XML content.
  2. No content linkable to the user. Generic config identical on every
     device (bundled reference data, A/B-test bucket ids, server bootstrap
     URLs, ML models) doesn't count.
- It's a denylist: an unrecognised subfolder stays in scope.
- `mobile/Library/Caches/` is in scope with 24 subfolders excluded. Of the 19
  re-checked, five have real user-linked content and stay in: `GeoServices`
  (a paired Apple Watch's map cache), `com.apple.HomeKit` (home and
  accessory configuration), `com.apple.findmy.fmipcore` (the Find My device
  list), `com.apple.chrono` (renders of the user's widgets),
  `com.apple.ctcategories.service` (App Store lookups for apps the user
  viewed). `com.apple.AppleMediaServices` looked similar but held only
  generic experiment definitions, so it stays excluded.
- `com.apple.geod/` and `com.apple.MobileSMS/` stay in scope although their
  unknown-extension files look empty: their value is in known-extension
  files (`AP.db`, `MapTiles.sqlitedb`, `Previews/Search/*.png`), which the
  header scan never examines.
- `mobile/Media/`, `mobile/Library/ContactsMetadata/` and
  `mobile/Library/Passes/` were added after a real extensionless image in
  `ContactsMetadata/` stayed "Other". All three hold genuine user content;
  `Passes/` is real Wallet pass bundles.

**A-29. App containers get no exclusions.** *Confirmed (real), 2026-10-10,
every file checked.*
- Real Apple apps (`com.apple.mobilesafari`, `AppStore`, `Home`) have real
  content.
- Trap found: a 200-file sample wrongly flagged `com.google.Gmail` and
  `com.google.chrome.ios` as empty, missing 991 and 96 real pictures. Don't
  judge a container from a sample.
- About 700 tiny, empty PluginKit extension containers exist on every device
  (iOS scaffolding, not evidence). They are not listed: the list would be
  unmaintainable, go stale with each iOS release, and save nothing (mostly
  zero-byte files). And look-alikes such as `com.apple.stocks.widget`,
  `news.widget` and `weather.widget` hold real content.

**A-30. A completed tier can go stale.** *Confirmed (real), 2026-10-10:
one case claimed Tier 1 with 38,141+ candidates never scanned.*
- When a scan finishes, the number of qualifying files is stored with the
  tier (`header_scan_candidate_count`). On load it is recomputed. A gap, or
  a legacy case with no stored count, turns the banner red with the gap
  stated, and Process Case lets the examiner re-run that tier through the
  normal upgrade path.
- Nested-archive and embedded-media files are unaffected: they are typed
  when extracted (1,281 real nested files checked, zero mismatches).

**A-31. PNG and GIF are type "Graphic"; TIFF and RAW are "Picture".**
*Decision, 2026-10-11.*
- Applied in both places a type comes from: `_EXT_TO_TYPE` (by extension)
  and `header_scan.classify_magic` (by magic bytes), so an extensionless
  PNG gets "Graphic" too.
- Why: the Media Browser's Graphics bucket must be expressible as a plain
  Type filter; filtering by extension would miss files typed only by their
  header.
- `.tiff`, `.tif`, `.raw`, `.cr2`, `.nef` and `.dng` were added to
  `MEDIA_EXTENSIONS` so the Media Browser shows them.

**A-66. Coverage is shown to the examiner, in the same terms the rules
use.** *Decision.*
- Process Case's "Scanned Folders…" dialog lists the included folders, the
  excluded subfolders and any embedded-media-only exclusions. It says "no
  recognisable file content", never "no media" (A-28).
- The User Media "Folders…" dialog lists `user_media_folders()`. Its
  exclusions are read from `user_media_ignore_list.load()`; there is no
  second list (A-27).

## 9. Recovering media embedded inside other files

**A-32. The embedded-media sweep is schema-agnostic.** *Decision.*
`app/embedded_media_scan.py` finds real images and video inside SQLite BLOB
cells and plist NSData values. SQLite's record format records each field's
type and length, so no knowledge of the app or table is needed.
- **Live content:** a real SQL query per table
  (`artifact_runner.open_db_readonly`), so SQLite itself follows a BLOB's
  overflow pages and a full-size photo is recovered whole. Every column of
  every row is checked; no sampling.
- **Deleted content:** reuses `sqlite_carve.py`'s carving (freelist pages,
  WAL frame history) unchanged. Small deleted items (thumbnails, stickers)
  are recovered.
  - Known limit: a deleted photo big enough to have needed overflow pages
    is not recovered.
  - Known limit: a single-row `DELETE` on a page that's still in use is not
    recovered without the table's schema; per-app `recoverable_tables`
    parsers cover that.
- **plist:** NSData values are checked, including a bplist nested inside an
  NSData (real in iOS `_atsContext`-style fields).
- **HTTP-wrapped blobs:** a stored HTTP response is unwrapped (headers
  removed, body decompressed via `artifact_runner.decompress_http_body`)
  before checking.

**A-33. Results are precious findings.** *Decision.*
- They go in `caseresults.db` → `embedded_media_hits`, with
  `UNIQUE(source_ui_path, location, sha256)` so re-runs never duplicate.
- A hit shows in the Media Browser's "Embedded Media" view and as a virtual
  child of its source file in the File Browser.
  - A live hit is named `<db>-<column>-<rowid>`.
  - A carved hit is named `<db>-carved`: no column/rowid, since a carved
    hit's identity is less certain.
- `processing_registry` (in `casecache.db`) records which files were swept
  under which version of the sweep. The version is a hash of the module's
  own source, so improving the sweep automatically re-offers every file.

**A-34. Noise control: two examiner-curated lists, neither silent.**
*Decision.*
- `embedded_media_skip_list.py`: databases not to scan at all (e.g. an SDK's
  own icon cache), checked before the file is read. Split by platform.
  Matches by basename, path fragment or wildcard. Entries made by
  right-click are app-scoped, so excluding one app's copy of a shared
  filename never excludes another app's.
- `user_media_ignore_list.py`: a global exclusion list for the "User Media"
  filter, checked into the repo as shared knowledge. Hidden files stay
  reviewable via "Show Media Excluded by Ignore List…".
- Both store app paths by bundle id, never GUID (A-8). Both compare the
  candidate after converting it the same way (`canonical_app_path`).
  Confirmed (real): a GUID-based entry already in the shipped list could
  never have matched again, and the skip list's app-scoped entries never
  matched anything until candidates were converted too.

**A-35. A wildcard ignore rule needs a structural anchor, checked against
every file it matches.** *Confirmed (real), 2026-10-10: 3 iOS and 3 Android
devices, 49,840 and 33,091 User Media candidates.*
- Shipped:

  | Pattern | Label | Why it's safe |
  |---|---|---|
  | `*@2x.png*`, `*@3x.png*` | UI Graphics | Apple's Retina asset naming, PNG only |
  | `*__MACOSX/*._*` | Zip Metadata (macOS) | AppleDouble sidecars; all 2,814 real matches in one archive carried the signature |
  | `*.9.png` | UI Graphics (nine-patch) | Android's reserved stretchable-UI format |
  | `*/drawable-*dpi*`, `*/mipmap-*dpi*` | UI Graphics (Android resource) | Android's reserved density folders |

- Rejected, with evidence:
  - **"Duplicate filename = chrome."** The biggest duplicate cluster,
    `5005.JPG` (2,491 files), is iOS's per-photo thumbnail name: real
    photos.
  - **"No EXIF = chrome."** Real photos that passed through a messaging
    app's re-encode have no EXIF: exactly the received/shared photos that
    matter.
  - **`@2x`/`@3x` on any extension.** The 8 `.jpg` matches out of 6,081 were
    real Edge/Chrome tab snapshots (renders of the open page), hence PNG
    only.
- Lesson: only "how the file got onto the device" (a build or packaging
  convention, never re-encoded) has proved safe. Content signals (EXIF,
  size, colour depth) have not.
- A pattern without a trailing `*` must match the end of the path
  (`version1.9.pngBACKUP.zip` used to match `*.9.png`). Say "more can
  follow" explicitly with a trailing `*`.

## 10. Review features (Media Browser, File Browser)

**A-36. Media Browser buckets.** *Decision, 2026-10-11.*
- Picture / Video (mov, mp4, m4v, 3gp, avi) / Graphics (PNG, GIF), each
  with its own default sort:
  - Pictures and Videos: newest first.
  - Graphics: largest first, since a tiny PNG is more likely an icon.
- The video-play badge is a different question: "could the first frame
  hide something?" It applies to real video or GIF regardless of bucket.
- The type filter resets to "All" whenever a new folder or view is opened.
  A refresh of the same folder ("Not Relevant", Undo) keeps it. Not
  resetting made a later folder look empty.
- The status line counts files hidden as "seen" and files hidden by the
  type filter separately.

**A-37. Filter+sort presets are shared by the File Browser and the Media
Browser.** *Decision ("fully unify both"), 2026-10-11.*
- One store, `app/file_browser_presets.py` (JSON, checked into the repo).
- A preset is `{name, date_filters[], type_filter, text_filters[], sort[]}`.
  - Filters within a list are ANDed; the values inside one text filter are
    ORed.
  - Sort levels are applied least-significant first, relying on Python's
    stable sort, so each level gets its own direction.
- A preset is a separate mode from the plain filter bar (picking one
  disables the bar), and it survives folder navigation: every rebuild of
  the file list goes through `_apply_active_filter`.
- The Media Browser's buttons read the live "Pictures", "Videos" and
  "Graphics" presets. If one is missing, unusable or unreadable, they fall
  back to built-in defaults: a button must never go blank because a preset
  was edited.

**A-38. Hover-scrub in the video viewer.** *Decision, 2026-10-11 (modelled
on Griffeye).*
- The pointer's horizontal position maps to a position in the clip (left =
  start, middle = halfway).
- The playhead moves toward that position at a capped rate (a full sweep
  takes at least 2.5 s, 40 ms ticks), so frames sweep past rather than
  jumping.
- Moving backward is just an earlier seek. True reverse playback (a
  negative playback rate) is unreliable across Qt backends and is not used.
- Only active while paused, so it never hijacks real playback. Leaving the
  video stops it.

**A-39. EXIF / video-metadata columns.** *Decision, 2026-10-11.*
- A Process Case stage, ticked by default. It runs last, so nested-archive
  and embedded-media files are available. Its scope is the same as the
  header scan's (`scan_folders`/`scan_excludes`).
- Columns are suffixed "(EXIF)" so they never clash with the existing
  Photos.sqlite-based Taken/Camera/GPS/Place columns, which apply only to
  Photos-indexed images.
- Facts that shaped it, all *Confirmed (real)*:
  - The cost is I/O, not decoding. Reading lazily touched 0.22% of a 102 MB
    video (6.2 ms against 25.2 ms for a full read).
  - Files without EXIF cost the same as files with it, so there's no
    cheaper pre-check to add.
  - HEIC (iOS's default photo format) needs `pillow_heif` registered in this
    Qt-free module. Without it, all 139 real HEIC photos in one folder
    silently returned nothing.
- Nested-archive and embedded-media candidates are collected when the stage
  runs (passed as a function, not a list), so hits found earlier in the same
  run are included.
- Stored in `casecache.db` → `media_metadata`: it can be rebuilt from the
  archive.

**A-40. LevelDB/IndexedDB indexing is an explicit Process Case stage.**
*Decision, 2026-10-12.*
- It used to start automatically at case load, competing with the Process
  Case dialog that opens at the same moment. It now runs first in Process
  Case and is ticked by default.
- It runs on the main thread in short time slices, because it reads through
  the GUI's shared archive reader and background workers must own their own.
- Cancelling never writes the "fully covered" marker, so unreached folders
  stay reported as unindexed (*Confirmed (real)*).
- The Keyword Search tab is disabled only while the stage runs.

**A-41. "Linked Report" relies on report rows being numbered in insertion
order.** *Decision, 2026-10-12; the numbering is Code only.*
- `artifact_db.build_attachment_links` assumes the n-th row it is given gets
  SQLite rowid n in `artifact_<script>`. That holds only because:
  - `write_artifact_results` drops and recreates the table with no explicit
    primary key;
  - both functions receive the identical `rows` list in the same order.
- If wrong: if `write_artifact_results` ever changes (a primary key,
  de-duplication, a different insert order), every link silently points at
  the wrong row. Verified (real) on one parser run: the linked row id named
  the exact same message.
- The label is the report's display name, the same for every link from that
  report, so a filter like "sms" finds them all.
- Links are rebuilt per script on each parser run and stored in
  `caseresults.db` → `artifact_attachment_links`.
- *Decision (owner), 2026-10-21:* every artifact report whose rows point at
  files in the archive must link them this way, not just iOS SMS. The
  mechanism is already generic (any parser declaring `media_fields`), but:
  - 9 parsers declare `media_fields` (iOS: sms_messages, whatsapp,
    photos_metadata; Android: google_messages, whatsapp, chrome_cache_pages,
    chrome_cache_media, chrome_favicons, chrome_offline_pages); only iOS SMS
    has been checked on real data;
  - the other 30 parsers declare none; any that reference files need it.
  Tracked in IDEAS.md idea 4; the rule for new parsers is in
  WRITING_ARTIFACT_PARSERS.md (`media_fields`).
- *Fixed 2026-10-22, verified on all six test archives:*
  - GrayKey iOS: paths built from `mobile/...` (SMS attachments, Photos)
    didn't exist there (`private/var/mobile/...`), so they neither opened
    nor linked. `FfsAdapter.ui_path_for` now translates; the runner passes
    the translated `_app_base_ui_path` and `_ui_path_for` to parsers.
    IOS18: Photos 0/6 → 6/6, SMS 0/1 → 1/1.
  - New optional `link_fields`: the column holding the archive file a row
    came from, when `media_fields` points at a decoded copy on disk. Chrome
    cache media and pages link `raw_ui_path` (0 → all, e.g. 14,860 on
    Android 15 CTF25); Chrome favicons declare `[]` (one database, no
    per-row file).
- *Not a bug:* Photos rows whose original isn't in the extraction (IOS17 10
  of 567, CTF23 146 of 1,918). None are in Recently Deleted; each has a
  same-named file under PhotoData, likely a derivative (e.g. iCloud
  "Optimise Storage"). Unverified beyond the name match.

**A-69. Duplicate detection.** *Decision; Confirmed (real) on CTF26,
2026-10-16.*
- A Process Case stage (`duplicate_scan.py`), run last. Files are grouped
  by size + CRC32, both free from the central directory; only files that
  land in a group are MD5-hashed to confirm, since CRC32 alone can collide.
- Files sharing a trusted inode (A-67) are the same file, so they reuse
  one MD5: CTF26 went from 121,382 reads to 42,492 with identical results.
- Covers the whole archive, deliberately not limited to the scan folders:
  an app's cached copy of a user photo can sit anywhere.
- Candidates are resolved with `resolve()` + `getinfo()`, not
  `build_zip_entries()`, which returns nothing for GrayKey (its paths
  have a leading slash).
- Results are kept in `casecache.db` → `duplicate_files` and loaded when
  the case opens; nothing is recomputed on open. Running the stage again
  clears and rebuilds them completely, so no stale group survives. That's
  cheap: about 10 s for CTF26 (39 GB, 131,397 files).
- The checkbox starts ticked for a new case and unticked once a complete
  run's results are on record (*Decision, 2026-10-20*): the archive never
  changes, so a later Process Case run shouldn't silently redo it. The run
  log (`caseresults.db`) alone isn't enough, because `casecache.db` can be
  recreated; the results must still be present too.
- GrayKey (*Decision + Confirmed (real), 2026-10-20*): a size+CRC group
  whose every member has a recorded SHA-256 (A-73) is grouped on it with
  no reads. Those results keep the 64-char SHA-256 in the table's `md5`
  field (no schema change); the "MD5" column shows only real 32-char MD5s.
  CTF26: identical groups to the MD5 run, 0 files read, 0.1 s instead of
  about 10 s. Groups with any member lacking a hash take the MD5 path.
- Folder entries are never candidates. GrayKey's root folder `/` used to
  join the size-0 group and was listed as a "duplicate" of 5,561 empty
  files (fixed 2026-10-20).

**A-70. Duplicates are hidden only in the Media Browser.** *Decision (owner
correction), 2026-10-17.*
- The File Browser always lists every copy, with "Duplicate Count" and
  "MD5" columns.
- The Media Browser's "Hide Duplicates" (ticked by default) shows one
  thumbnail per MD5 group: the first copy in the current view's own list,
  not one chosen for the whole archive, which would make a file vanish
  from a folder that only holds another copy.
- Collapsing runs before the "seen" filter, so a group whose shown copy
  is "Not Relevant" stays hidden rather than another copy surfacing.
- While it's on:
  - Bookmarking a shown copy bookmarks every copy archive-wide: fewer
    thumbnails to review, but every location of an important file is
    kept.
  - "Not Relevant" marks every copy too, except bookmarked ones, in the
    same Undo batch. Verified (real), CTF26: one 500-thumbnail page
    marked 500 shown files plus 1,084 hidden copies.
  - The bookmark panel shows "User Media (N · M to review)": N is what
    clicking selects, M the thumbnails left after collapsing. Both use
    `_collapse_duplicate_paths`, so M always equals the grid's count
    (CTF26: 3,913 · 3,609).

**A-71. The "User Media" count depends on header-scan types.** *Confirmed
(real), CTF26, 2026-10-17.*
- `_is_media_file` counts a header-detected picture or video as media, so
  the count is only right once `_header_type_overrides` has loaded.
- The panel used to count at tree-done, before the background load: CTF26
  showed 1,294 while clicking selected 3,913 (0 vs 5,049 overrides).
- The panel is now refreshed after that load and after every change to
  the header types.

**A-74. Files unpacked from nested archives are typed at unpack time and read
by the later stages.** *Decision (owner report) + Confirmed (real),
2026-10-22.*
- Process Case runs the header scan before unpacking, so it never sees
  unpacked files. Unpacking now types each one the way the main archive is
  typed: extension first, then `classify_magic`, then the text check for a
  small file (`nested_archive.classify_unpacked`).
- `nested_archive.unpacked_file_index` maps each File Browser path
  (`{archive}/{entry}`) to its unpacked archive and type. The embedded-media
  sweep merges those types and reads the bytes from there; before, it typed
  unpacked files by name only and every read silently failed.
- Verified: 40 unpacked archives each on IOS18 and CTF23 — sweep candidates
  66 → 211 and 35 → 303 (now including databases), every one read; Android
  14 JoshHickman: 442 small text files now typed Text.
- Duplicate detection includes unpacked files (owner request, 2026-10-22):
  `nested_archive.unpacked_duplicate_candidates` gives size + CRC from the
  repacked zip (computed once for a gzip blob) and a reader, so they group
  together with main-archive files. A group containing any unpacked file
  uses MD5 (they have no GrayKey hash). If a run unpacks new archives,
  "Detect duplicate files" is re-ticked for that run. Verified on IOS18
  with 40 unpacked archives: 403 groups include unpacked files, 290 of them
  with main-archive files; every member of those 403 groups shares one MD5
  (independent check); main-archive groups otherwise identical (11,875).
- EXIF/video metadata already had its own route for unpacked files.

**A-75. Web cache records (any app) show their media as children.**
*Decision (owner) + Confirmed (real), 2026-10-22.*
- Chromium Simple Cache records (`<16 hex>_0`) are used by Chrome and by
  every app with a Chromium WebView or engine (Edge, Opera, Brave,
  DuckDuckGo, Instagram, Imgur, WeChat, Fitbit, Facebook Messenger, ...).
  The embedded-media sweep nominates them by name and accepts them only
  with the format's magic; a body that is an image or video becomes the
  record's child (`source_kind` 'cache').
- The child is named from the URL, carries **Source URL**, and takes
  **every time field of its record unchanged** (all four on GrayKey,
  mtime only on Cellebrite Android), because one record holds exactly one
  cached download. Only cache records do this; database/plist hits don't
  (their container times describe the whole container).
- Server `Date`/`Last-Modified` are not columns (server clock, about the
  website); they are in the record's Text tab with every other header.
- Double-clicking a record goes inside it and shows the record's
  information (URL, raw cache key, status, content type, sizes, headers,
  any parse/decompression problem) in the Text tab. The child's Text tab
  says which record it came from and that its times are the record's.
- Cache media is left out of User Media (not user-created content).
- Cache keys of the form `1/0/<url>` (no partition) had the flags prefix
  left in the URL; now stripped when a URL scheme follows. This also fixes
  the Chrome Cache Media/Pages reports' URL column on re-run.
- Verified: CTF26 12,075 records → 2,670 media, all times equal to the
  record (Created/Changed/Accessed/Modified); Android 14 JoshHickman
  16,037 → 2,088 (Modified only); every child real media with a clean URL.
- Not handled: media stored in sparse `<hash>_s` files (common for video).

## 11. In-app format decoding

**A-42. Binary plists:** decoded with `plistlib`, with NSKeyedArchiver
handled through `nska_deserialize` (`artifact_runner.decode_plist_blob`).
*Confirmed (real).*
- A real stdlib defect: one CFDate outside Python's date range makes
  `plistlib` discard the whole file.
- Worked around per field by `_read_binary_plist_tolerantly`, ported from
  iLEAPP.

**A-43. Android Binary XML (ABX):** decoded by vendored `app/ccl_abx.py`
(from ALEAPP). *Confirmed (real).*
- Two real bugs were fixed in the vendored reader before trusting it:
  - a signed/unsigned 16-bit length mix-up that silently cut off the rest of
    a document after one long value;
  - a missing retry for multi-root documents.
- Re-run with zero regressions across hundreds of real ABX files.

**A-44. LevelDB and IndexedDB.** *Decision.*
- A LevelDB-shaped folder decodes the first time it's opened. Each record
  becomes a virtual file (key as name, value as content) using the same
  mechanism as an extracted nested archive.
- IndexedDB uses a real schema-aware decoder, vendored
  `ccl_chromium_indexeddb.py` pinned to an upstream commit.
- Every other LevelDB store goes through `classify_leveldb_value`. It
  accepts only what passes real JSON/XML/plist/protobuf structural checks,
  and otherwise shows a labelled hex dump; it never guesses.

**A-45. Protocol Buffers have no general decoder:** there's no schema to
decode against. *Decision.*
- SEGB payloads use `blackboxprotobuf`'s schema-less decode.
- The LevelDB classifier only recognises protobuf-shaped values (scanning
  varint tags and wire types) and labels them, rather than showing them as
  garbled text.

**A-64. Images are decoded through one function, `_load_qimage`.**
*Confirmed (real).*
- It applies EXIF/TIFF orientation through `QImageReader.setAutoTransform`.
- Qt has no native HEIC codec on Windows, so if Qt can't decode a HEIC/HEIF
  file it falls back to `pillow_heif`.
- Thumbnails and the full-size viewer both go through it, so they can't
  disagree.

## 12. Artifact parsers and SQLite evidence

**A-46. Opening an evidence SQLite database can destroy evidence.**
*Confirmed (synthetic test).*
- A plain `sqlite3.connect()` can checkpoint and delete a `-wal` sidecar on
  close, even after only reading, destroying deleted-record traces.
  `open_db_readonly()` uses a `file:...?mode=ro` URI.
- An `ATTACH`ed second database is **not** read-only just because the main
  one is; it needs its own `mode=ro` URI. *Confirmed (synthetic test).*
- Carve WAL/SHM sidecars before any connect.

**A-47. Carved rows are labelled, never dropped.** *Decision.*
- A `header_signature` match (the weakest of the four carving methods: no
  rowid to cross-check) is labelled `(unverified match)`.
- Any carved row failing the table's own NOT NULL or timestamp-plausibility
  checks is labelled `(likely false positive — reason)`.
- Both are still shown.

**A-48. Report timestamps are stored raw.** *Decision.*
- Parsers store raw values and declare the unit (`timestamp_fields`); the
  display format is applied per the case's timezone setting.
- One exception: `photos_metadata.py`'s Taken/Added, which merge into the
  File Browser by a different route.

**A-49. Attachments are linked only when they are real local paths.**
*Decision.* `media_fields` is declared only for a real local path (not a
`content://` or remote URI), and only after checking that the constructed
path resolves against real archive bytes.

**A-50. Absence of evidence needs checking.** *Decision.* Before concluding
an app has no evidence, check for extensionless files (`evidence_databases`
is magic-byte aware) and unextracted embedded archives
(`embedded_archives`).

**A-51. Escalate, never silently truncate or discard.** *Decision.* A list
capped for display says there is more and offers the rest. A low-confidence
item is labelled with the reason. Several features were redesigned to stop
silently truncating once this was pointed out.

**A-52. AI Summary may only describe a row using words that appear in it.**
*Decision; three real hallucinations led to it.*
- The three: an inferred (wrong) sports team, an invented category grouping
  unlike items, and two similar-titled rows merged into one claim.
- Grounding a fact and characterising what it means are different claims.
  Test both against real data before trusting a prompt change.

## 13. Case data storage

**A-53. Two case databases, by how replaceable their data is.** *Decision.*
- `casecache.db`: rebuildable from the archive, so it is safe to delete;
  deleted and rebuilt on a schema mismatch. Holds thumbnails, blobs,
  `header_types`, `guid_bundle`, the nested-archive index,
  `app_intelligence`, `app_registry`, `evidence_page_map`,
  `leveldb_search_index`, `processing_registry` and `media_metadata`.
- `caseresults.db`: examiner work and findings, never deleted
  automatically. Holds search results, bookmarks, `device_info`, `run_log`,
  `segb_schemas`, `case_settings`, the `artifact_<name>` tables,
  `ai_summaries`, `embedded_media_hits`, `media_seen` and
  `artifact_attachment_links`.

## 14. Import Bookmarks (CSV/XLSX hash lists)

**A-54. A row is confirmed by re-hashing the file**, never trusted from the
spreadsheet's hash alone. *Decision.*

**A-55. How other tools write paths.** *Confirmed (real): a ProjectVic
export and a Griffeye export, matched against a Cellebrite-layout iOS
archive.*
- **Archive name as first segment:** a path's first segment is often the
  archive's own filename. It is stripped before matching.
- **Separate folder and file columns:** Griffeye can put folder and filename
  in separate columns. They must be joined before matching; the first
  release matched on the folder alone, and every row silently failed.
- **Parent folder prefix:** Griffeye can also prefix the folder the zip sat
  in ("Remove parent folder from Filepath").
- **Griffeye's "root/" marker:** Griffeye writes `private/var/mobile/...` in
  full, plus its own "root/" marker for the top of the filesystem. That
  clashes with this app's ui_paths, where `private/var/root` is collapsed to
  `root` (A-6). `ios_path_candidates` tries each interpretation and keeps
  whichever resolves.

**A-56. Group filtering and presets.** *Decision.*
- The group checklist filters only once something has been unticked. Left
  fully ticked it filters nothing, so blank cells keep falling back to the
  default group.
- Saved mapping presets live in `QSettings` and match columns by name (not
  position). One is auto-applied only when exactly one preset fits the new
  file.

## 15. UI behaviour decisions

**A-57. Tabs keep their state.** *Decision.*
- The four centre tabs resume exactly where the examiner left them unless
  the underlying data changed. `_on_center_tab_changed` is the one place
  this lives.
- The bottom preview panel (Hex/Text/Database/SEGB) is shared by all four
  tabs, so each tab re-applies its own last preview when shown. A tab's own
  widgets need nothing.

**A-58. Bookmarks.** *Decision.*
- A file in two or more groups shows equal colour bands, one per group, in
  the File Browser Name cell. The Media Browser's badge stays single-colour.
- The group highlight follows whether the current selection still overlaps
  the group at all. It is re-checked in `_refresh_file_checked_paths` and
  only ever clears. It must be set after
  `_replace_selection_from_bookmark_entries` runs (which clears first).

**A-59. Tree selection.** *Decision.*
- **"Only Show Selected":** hides unselected files, never folders; off by
  default. A bookmark-group click resets it to off; "User Media" turns it
  on. It applies only in the "Selected Only" branch.
- **Switching between the two tree branches:** first try the exact path that
  was selected; then that branch's own last selection; otherwise select
  nothing.

**A-65. Report column visibility lasts only for the session; column order
is saved.** *Decision.* A hidden column must never silently stay hidden
forever (`report_columns_store.py`).

**A-60. A menu is never hidden because of one feature's setting.**
*Decision.* Toggle that feature's own actions instead. Hiding the whole
Tools menu when AI access was off once hid every other Tools action too.

## 16. Environment facts (Qt, macOS, Python, PyInstaller)

**A-61. Qt quirks.** *Confirmed (real) for each.*
- **macOS checkboxes:** `QMacStyle` sometimes doesn't paint tree/table item
  checkboxes at all. Force `QStyleFactory.create("Fusion")` on that view and
  keep the style object alive (`setStyle` doesn't take ownership).
- **Widgets embedded on tree rows:** in a widget set with `setIndexWidget`,
  never put a stretch before the real content. The column is wider than
  the view, so it pushes the content out of sight.
- **Rebuilt subtrees don't expand:** after rebuilding a subtree under
  `blockSignals(True)`, `expand()` can silently fail on a second or later
  rebuild. Call `doItemsLayout()` first.
- **Horizontal scrolling:** `QTreeView.scrollTo(..., EnsureVisible)` only
  scrolls vertically. Set the horizontal scrollbar yourself.

**A-62. Headless test pitfalls.** *Confirmed (real).*
- **`isVisible()` always false:** under the offscreen platform it is false
  until the top-level window is shown; call `window.show()` first.
- **Modal dialogs block forever:** a modal `exec()` blocks indefinitely with
  nothing to click. Neutralise every modal the code path can reach (the
  first-load Timestamp Display prompt is easy to forget).
- **The script runs twice on macOS:** the default `spawn` start method
  re-imports a standalone script as `__main__` in the metadata-parse child
  process, running it again. Guard with
  `if multiprocessing.current_process().name != "MainProcess": sys.exit(0)`.

**A-63. Windows build.** *Confirmed (real).*
- **Which spec CI uses:** CI (`build-windows-exe.yml`) runs
  `pyinstaller ffs_explorer.spec`; that's the spec that matters.
- **HEVC video:** the prebuilt PyAV wheel can't decode HEVC (iOS's default
  video codec) on at least macOS, so CI builds `av` from source. A dev
  machine's wheel is not what ships.
- **Silent exclusions:** a stale `'PIL'` entry in the spec's `excludes=`
  once silently removed a real dependency. After adding a dependency, check
  `build/ffs_explorer/warn-ffs_explorer.txt` after a clean rebuild.
- **Config files must be listed:** a config file is shipped only if listed
  in `datas=`, and the destination must match its module's `store_path()`.
  - `scan_rules.py` reads from `config/` → destination `'config'`.
  - `user_media_ignore_list.py` and `file_browser_presets.py` read next to
    the exe → destination `'.'`.
  - Missing the scan-rules files once shipped an exe with nothing in scope
    for the header scan or User Media. Dev runs can't catch this.
